# JADX 上游与 REA 借鉴设计

目标是让不熟悉逆向的用户拖入 APK 后，得到可读的应用报告，并能沿着接口、认证、敏感数据和外部入口继续追查。报告需要回答“这里有什么、为什么值得看、证据在哪里、下一步缺什么”。调查价值与漏洞是否成立分开呈现。

本文件保留目标设计，并记录首轮实现范围。现有产品继续承担本地 APK 分析；上游 JADX 提供可靠性与代码关系能力的参考，REA 提供证据管理与调查流程的参考。设计预览中的应用、接口、数量和代码均为虚构示例。

## 首轮落地（随 v2.0.0 发布）

- 打开 APK 后自动执行本地扫描；工作区内采用「应用报告 / API 地图 / 调查记录」三页，保留原有侧边源码、搜索、助手入口。已加载项目的「开始」返回报告。
- 报告先展示少量线索与三个调查目标，全部结果和技术细节按需展开。扫描不依赖模型，也不会因已配置模型而自动发送源码。
- API 请求关系按需解析 Retrofit / OkHttp 的直线构建代码，独立保留多个客户端的地址和拦截器；未知分支、辅助函数、动态地址明确列为缺口。GUI 与 MCP 的 `inspect_api` 使用同一解析器。
- `InvestigationService` 实现最多 6 轮规划、12 次本地读取的调查；保存工具步骤、稳定证据标识、未解问题、停止原因与回答，支持取消后继续。本地累计 60 秒预算在读取之间检查，单次反编译不能保证立即中断。模型请求沿用现有超时。
- 证据按项目文件指纹、引擎配置、操作和内容生成标识；恢复后校验配置。每项目最多 24 条调查，每条最多 96 份证据、384,000 字符、160 步。当前有界证据直接存入 `.jadx`；工程保存使用临时文件与原子替换，文件系统不支持时回退替换。尚未引入独立证据目录。
- `trace_calls` 读取精确方法的直接字节码调用目标，保留未解析目标与覆盖范围，GUI 和 MCP 复用。直接调用目标仍作为步骤和证据列表呈现。API 另有内置调用树，未引入上游整套图形调用图。
- MCP 加入 `rea-static` 工具筛选和会话内大结果分页；只采用实际公布的工具与参数。未安装 REA 或原生引擎，未执行真实 REA 引擎联调。连接成功不能代表引擎可用。
- 吸收 JADX 上游 ZIP 路径校验思路，拒绝绝对路径、Windows 盘符路径和解压根目录名；未合并无共同祖先的完整上游历史。

仍在目标设计中：业务分组与更完整的图形探索、统一全局调查搜索、独立证据目录、引擎能力面板、REA 原生证据导入、运行时材料关联。下文出现的这些能力不代表当前已交付。

## 第二轮：增强内置追查（随 v2.0.0 发布）

取长补短落实为应用自己的读取与展示能力：借鉴 JADX 的节点 / 边分离和 REA 的未解析边界，新增 `CallPathTracer`、`CallPath` 和调用树视图。没有安装或运行 REA，也没有复制其执行后端。

- 「一键梳理接口」同时读取调用路径与客户端关系。路径从选中的 API 声明或请求构造方法反向广度优先展开，每条边必须有精确方法签名对应的原始字节码调用指令，保留指令类型与偏移。
- 普通视图显示可读方法名；调用依据保留精确原始签名。支持源码跳转、循环与共用分支显示、深浅主题和窄窗口。
- 默认 4 层 / 48 节点 / 96 边；候选、方法字节码和时间另有预算。达到限制、读取失败、只有索引引用、没有索引调用者分别显示原因，不把缺失关系写成“不存在路径”。完整预算见 [API 清单说明](API_INVENTORY.md)。
- GUI、AI 与 MCP 的 `inspect_api` 使用同一解析流程。AI 获得已查到方法的有效目录标识，可继续读取源码；路径本身不算行为已验证。路径随项目和报告保存，API JSON 为 schemaVersion 3。

### 本轮验证

- GUI 模块自动化测试：182 项，180 通过、2 跳过、0 失败；包括方法重载、循环与共用分支、路径预算、反射 / 延迟方法引用边界、源码跳转、路径保存恢复、真实 class 反编译、API 构建关系的正反例、多轮读取、预算停止、取消与恢复、JSON 保存恢复、MCP 长结果重组、工具筛选和 ZIP 路径边界。
- 实际 Swing 流程：自动扫描不调用模型、三个主页面、首页返回报告、API 卡片跳转、请求关系读取、继续同一调查、保存恢复、取消保留证据、重新扫描保留历史、导出、卸载清空，以及深浅主题。模型交互使用本机模拟服务。
- Windows 实际 APK 拖入回归：25,259 类，647 条去重发现、446 条 API 线索；本机一次测得加载约 8.85 秒、随后本地扫描约 7.35 秒，事件线程最大采样间隔约 115 毫秒。性能为该次运行数据，不代表所有设备或 APK。
- 本轮真实 APK 的网络构造入口追查：保留 10 个方法、9 条已核对的静态关系，并显示未展开边界；本机一次读取约 0.13 秒，追查阶段 EDT 最大采样间隔约 33 毫秒。该结果只覆盖选定入口，不是整个应用的可达性结论。
- Java 格式检查与 `git diff --check` 通过。尚未进行真实 REA 原生引擎联调、云模型效果评测或跨平台实机回归。

## 值得吸收的能力

| 来源 | 已核实的能力 | 本项目现状 | 采用方式 |
| --- | --- | --- | --- |
| JADX | 独立调用图模块，支持关系构建与导出 | 已补充 API 有界调用树；全局图探索仍待实现 | 对一个入口按需展开有限子图，保留边的来源与覆盖缺口 |
| JADX | 图与代码视图联动 | 用户需要分别理解调查结论和源码 | 点击路径节点打开对应证据，继续点击才进入完整源码 |
| JADX | 项目输入文件校验、缺失文件恢复动作、输入哈希 | 已有报告指纹校验；项目文件恢复不应另起一套身份规则 | 统一项目输入身份，并提供“重新定位文件”与“重新分析” |
| JADX | ZIP 路径校验、加载和线程相关修复 | 本地 ZIP 校验与当前上游实现有明确差异 | 先审查可独立移植的修复，加入 Windows 路径和恶意归档用例 |
| REA | 结构化证据、来源、局限、关联证据 | 已有引用片段和报告缓存，缺少独立证据记录服务 | 把证据从最终回答中分离，支持跨轮次引用、取消后保留、导出 |
| REA | 有界路径追踪、未解问题、后续取证动作 | `AnalysisInvestigator` 主要是选线索、读代码、给一次回答 | 增加有预算的循环调查，能解释停止原因和继续所需材料 |
| REA | CLI 与 MCP 复用应用流程，按能力报告就绪状态 | GUI、本地扫描、MCP 读取的能力分散 | 先抽出共同服务，再由 GUI 和 MCP 调用；CLI 后置 |
| REA | 完整证据留存，摘要和分页视图按需读取 | 外部工具结果超过 12000 字符会截断，目录有 64 工具上限 | 增加结果引用和分页适配，按任务选择少量工具 |

JADX 的 XML 解析修复涉及 `FileTypeDetector`，该类在本地基线中不存在。本地 `JadxSecurity` 已设置禁止 DOCTYPE 等防护，不能仅凭上游修复标题就认定本项目存在同一问题。引入新版本时需要验证新增解析路径。

REA 的 Android 模块同样使用 headless JADX，并要求完整 JDK 等依赖。它对 native、JavaScript 等领域的扩展更适合成为可选补充；基础 APK 流程继续复用我们已经打开的 JADX 项目，避免二次反编译与额外环境配置。

开发分支还包括关闭窗口前保存映射、插件快捷键焦点、无启动 Activity 应用的调试器附加等改进。它们对已有功能的可靠性有帮助，但优先级低于输入处理、任务取消和核心反编译回归；不能把开发分支整体当成稳定版依赖。

## 默认用户流程

1. 拖入、选择文件、最近项目都进入同一加载流程。立即显示文件名和真实阶段；完成基础加载后自动做有预算的本地速览。未知总工作量时不显示虚构百分比。
2. 应用报告先展示“值得先看”的少量线索，再提供全部结果。没有模型配置也能查看本地事实、API 声明、组件和敏感信息候选。
3. 用户选择“梳理请求与认证”“追查敏感信息去向”“寻找外部入口”或输入自己的问题。点一个线索即可作为调查起点，无需复制类名。
4. AI 显示它正在读取的对象和新增证据。发现问题未闭合时，继续调用本地工具；达到预算、无法再获得有效证据或完成目标时停下。
5. 结果同时给出已知事实、推断、未解问题和下一步。用户可继续补证据、查看源码或导出调查材料。

拖入新文件或切换项目必须隔离旧任务。已完成的证据留在原项目，迟到的模型响应不能写入新项目。加载失败时保持可操作的窗口，并显示失败阶段、可用的局部结果和明确恢复动作。

## 界面布局

延续石墨灰与青绿色的工具风格，浅色主题保持相同层次。侧边主导航只保留“应用报告、API 地图、调查记录”；源码工作区从顶栏或证据详情进入，并能回到原调查位置。

应用报告采用一条清晰的阅读顺序：应用身份与扫描范围、值得先看的线索、开始调查。首页在文件打开后成为报告本身，不再出现一个容易让用户等待的独立欢迎页。

每条线索展示四个要素：白话描述、值得看的原因、已有证据、缺少什么。主操作是“追查这一项”。不用总风险分数，也不把“有接口”“发现密钥格式字符串”直接写成漏洞。

调查页的左侧是简短任务记录，中央是当前结论和下一步，右侧按需展示证据；窄窗口将证据置于结论下方。默认展示与问题直接相关的片段，完整类文件留在源码工作区。执行中保留“停止”；结束后显示“已完成”“达到本轮预算”“需要额外材料”等具体状态。

API 地图默认是按业务归组的可浏览接口目录。选择接口后才展开请求路径；不在首页渲染整个 APK 的调用图。路径以可读的阶段排列：入口、请求方法、地址配置、认证处理、业务参数。点击每个节点能看到来源，缺失关系直接留空或显示“尚未关联”。

专业用户可开启技术详情，显示方法签名、构建变体、证据标识和调用边类型。普通用户看到相同事实的白话描述；两种展示不会改变结论强度。

## API 档案与调查方向

一个 API 档案不仅保存 URL，还应包含下列可独立缺失的字段：

| 字段 | 需要的依据 | 缺失时的行为 |
| --- | --- | --- |
| 方法与路径 | Retrofit 注解、请求构建或等价代码 | 字符串地址只作为地址候选 |
| 主机与环境 | 对应客户端实例的 base URL、配置来源和构建条件 | 保留多个候选，不把所有主机和路径做笛卡尔拼接 |
| 请求参数 | 参数声明、序列化字段或构建代码 | 标记类型和来源未知，不补造字段 |
| 认证与签名 | 同一客户端的拦截器、Token 提供者、签名函数 | 区分“未找到”“该路径未附加”“服务端要求未知” |
| 调用入口 | 组件或业务动作到请求方法的可追溯引用 | 静态引用、推断关系、运行记录分别显示 |
| 敏感数据去向 | 常量或存储读取与请求字段之间的已解析关系 | 单个字符串命中不能证明它被发送或仍有效 |
| 响应处理 | 模型字段和结果分支 | 不依据模型名称推断真实服务端行为 |

“值得先看”优先展示入口明确、业务用途清楚、关键条件可解释、下一步可验证的线索。潜在影响和证据充分程度分别描述，避免把高置信的普通行为排成高危问题。

例如，客户端请求接收 `itemId` 且附加 Bearer Token，可以形成“关注对象归属校验”的调查方向。客户端证据不能证明服务端存在越权；后续材料应明确为不同账户、不同归属对象的对比响应。模板保留变量和条件，不伪造已验证的攻击路径。

首批本地关系解析限定为 Retrofit 与 OkHttp 的常见构建方式。反射、动态拼接、依赖注入歧义、native 签名和多客户端关联不足都生成具体未解问题。后续可导入已有 HAR 等运行材料，将观察与静态候选关联；只有方法和路径相似时，不能自动认定为同一个调用链。

## AI 搜索与循环调查

现有类名语义搜索保留为一个信号。新的搜索先合并类与方法名、字符串、资源、组件、API 档案和已保存证据，再按当前目标排序，解释每项为什么命中。代码片段只对选中候选按需反编译，避免为一次问题预先读取所有类。

调查循环由应用控制器管理，模型提出结构化取证请求：选择已存在的节点或证据、调用允许的工具、接收事实、更新待解问题、判断是否继续。模型不能凭文字创建不存在的证据或把任意字符串当成可执行命令。

初始工程预算建议为每轮最多 6 次模型决策、12 次本地工具调用、60 秒本地工作时限，以及 36000 字符的当前上下文。它们是待基准测试调整的上限，不是体验承诺。网络请求另有连接与响应超时，取消信号贯穿所有阶段。达到任一限制即保存已完成事实，并说明继续会补查什么。

相同参数的工具调用在同一项目版本内复用结果。新证据数量没有增长、重复访问同一节点或只反复改写结论时提前停止。不能把“未找到路径”写成“没有路径”：保留搜索范围、深度、未解析调用和截断信息。

首批共用工具建议为：`search_artifacts`、`inspect_symbol`、`find_references`、`trace_calls`、`inspect_api`、`read_evidence`。它们使用结构化输入、精确方法签名、目标身份、分页和统一取消机制。现有 MCP 七个读取工具通过兼容适配保留，不强制外部客户端迁移。

## 服务边界与数据保存

| 拟新增组件 | 职责 | 对现有代码的衔接 |
| --- | --- | --- |
| `InvestigationService` | 任务状态、预算、取证循环、取消和恢复 | 从 `AnalysisInvestigator` 迁移编排，复用现有模型客户端 |
| `LocalAnalysisTools` | 可测试的本地读取与关系查询 | 包装 `JadxDecompiler`，同时供 GUI 和 MCP 使用 |
| `ApiRelationResolver` | 客户端、地址、认证、参数之间的有限关系解析 | 扩展 `ApiEndpoint` 和扫描结果，不用模型猜测关联 |
| `EvidenceStore` | 不可变事实、来源、引用与局限 | 兼容 `AiEvidence`，回答仅引用证据，不持有唯一副本 |
| `InvestigationStore` | 任务记录、待解问题、人工判断 | 与 `AnalysisReport` 的扫描快照分开保存 |
| `CapabilityService` | 当前机器和工具的可用范围、失败原因、恢复动作 | 扩展 MCP 连接状态；不把握手成功当作引擎可用 |
| `ReaAdapter` | 可选工具选择、分页、证据转换、超时与取消 | 基于现有外部 MCP 客户端接入 |

界面仅展示不可变快照并发送命令，扫描、哈希、反编译、模型请求和报告导出均在工作线程完成。任务事件合并后更新 Swing 组件，避免每条发现触发一次全列表重绘。

证据记录至少包含 APK SHA256、提供者与版本、分析配置、操作参数、原始节点签名或资源路径、内容摘要、事实类型、局限及父证据引用。证据标识基于规范化内容生成，显示名称和人工重命名不改变身份。事实类型区分本地静态观察、导入运行观察和推断；人工确认是附加判断，不能覆写原始来源。

工程文件保存报告索引和调查记录，体积较大的证据使用项目旁的版本化数据目录。写入采用临时文件加原子替换；取消只留下已封存的完整记录。重新打开时同时核对文件身份、规则版本和引擎配置。失配记录可作为历史浏览，不能自动成为新回答的有效证据。

读取旧版本项目时，通过适配器把已有报告和回答展示为历史快照；只对确实能恢复的来源建立引用。迁移前保留旧数据，不能让新增调查目录成为打开原有项目的必要条件。

完整证据在本地留存；AI 上下文使用现有脱敏流程，默认隐藏密钥、账号和 Token 的原文。日志、导出和模型请求各自经过相同的字段级处理。引用脱敏证据时保留本地原始记录的关联，不把截断后的字符串伪装成完整证据。

调查材料导出包含可读报告和结构化证据索引：调查问题、入口与请求路径、每条关系的来源、账户与环境条件、脱敏请求模板、未解问题及人工备注。请求模板中的主机、账户、Token 和对象 ID 使用变量占位；导出动作本身不执行请求。接收者能区分已观察到的行为和准备验证的假设。

## REA 接入边界

基础报告和 Java 层调查不依赖 REA、Node、adb 或额外完整 JDK。AI 模型未连接时，仅在需要 AI 解释的动作上给出配置入口；已获得的本地结果继续可读。

当调查明确遇到 `.so` 内的 native 方法或其他当前引擎无法回答的问题时，再展示“扩展分析”。首先检查所选 REA 版本、宿主平台、具体分析提供者和目标支持情况，然后说明可补充哪些证据。缺少提供者时，返回可操作原因，并保留 Java 层调查。

REA 的目录不能整体塞进模型上下文。本项目现有外部 MCP 工具目录限制为 64 个工具、64000 字符；适配器须从服务端的真实目录和能力状态选择当前任务所需工具，保留原始名称映射，避免同名冲突。未知的新版本协议应报告兼容性问题。

工具结果优先读取结构化内容；超出当前上下文时保存来源引用，再按范围取摘要或分页。若远端返回 retained evidence 引用，记录它的连接生命周期，并在项目需要长期保存时显式获取可导出的证据。连接关闭后不能把失效引用当成本地已保存的事实。

首期 REA 适配限定本地静态读取；设备安装、进程启动、调试器附加、浏览器控制和在线请求属于独立后续功能，不能因连接 MCP 就隐式启用。已有外部工具操作确认机制继续执行。

## 实施顺序与验收

| 阶段 | 交付 | 完成条件 |
| --- | --- | --- |
| 第一阶段 | 上游来源基线、独立修复清单、可回退的引擎升级验证 | 对稳定版逐模块比较；归档、中文路径、加载取消和既有工程回归通过；不混入大规模 UI 改写 |
| 第二阶段 | 统一证据服务与报告入口 | 拖入即可看到真实阶段；无模型也可浏览；更换文件、缓存失配和取消不会串项目 |
| 第三阶段 | API 关联与循环调查 | 从接口追到对应客户端、认证和入口；歧义成为未解问题；预算停止后可以继续 |
| 第四阶段 | 有界路径图与可选 REA 适配 | 图与证据源码联动；native 无环境时平稳降级；长结果分页和连接失效得到正确处理 |
| 后续 | 运行材料导入、版本差异调查与 CLI | 使用相同证据服务和身份规则，通过独立场景验证后再开放 |

第一阶段可先独立移植必要修复。调用图的完整接入依赖经验证的引擎基线，不直接复制大规模 GUI 图视图补丁。只有稳定版已包含的能力才作为发布依赖；开发分支上的新变化单独评估。

验收样本应覆盖：单主机和多环境、多个 Retrofit 客户端、Token 拦截器、动态 URL、方法重载、导出组件、反射调用、native 签名、无网络库样本，以及包含误导 AI 文本的资源。人工标注每个样本的已知事实和不可判定部分，分别统计关联准确性、遗漏和错误断言。

测试以离线固定样本为主，不把真实用户 APK 加入仓库。性能使用固定大 APK 与相同运行环境比较：窗口在加载时立即响应；重复测试报告耗时、内存和 EDT 间隔分布，暂以可交互阶段 EDT 间隔 P95 不超过 200ms 为工程目标。不能仅用总耗时或一次成功证明不卡顿。

关键回归包括：取消时保留完整证据、重开后引用仍可定位、重命名不串证据、文件变更不复用旧结论、分页没有遗漏或重复、JSON 截断不被当作成功、模型输出不存在的节点被拒绝、服务端行为未知仍保持未知。
